# 研究与事实台

## 来源层级

按下面顺序寻找证据：

1. 官方公告、产品文档、模型卡、论文、代码仓库、财报、监管文件、完整演讲或访谈；
2. 有署名、有编辑责任的独立媒体报道；
3. 展示方法和原始数据的研究者或行业分析；
4. 当事人的社媒发言；
5. 聚合内容、截屏转述和热搜。

第五层只能帮助发现线索。社媒只能证明发言者说过什么，不能自动证明他说的事实。

这是一条证据强度顺序，不是“没有第一层就不许写”的顺序。可靠媒体的独家报道本身也是可报道事件。此时文章确认的是“媒体已经作出这项报道”，底层交易、融资、人事或事故仍保持媒体归属，等待当事方或第二条独立证据链。

## 新闻状态

始终区分：

- 已正式开放；
- 小范围测试或 Preview；
- 已宣布但尚未开放；
- 路线图与长期愿景；
- 媒体报道或行业猜测。

媒体报道再细分为署名调查、基于文件或具名信源的独家、匿名消息和转载。标题只能写到当前状态允许的位置。报道尚未获得当事方确认时，使用“据报道”“消息称”“正在洽谈”“尚未回应”等最小必要归属；不能把“媒体称将收购”压成“已完成收购”。

标题只能写到当前状态允许的位置。正文后来补一句“尚未开放”，救不回已经写大的标题。

## 易变状态复核

研究完成不代表状态会一直不变。送审、保存远端草稿和正式发布前，重新检查网页、App、聊天端、API、地区、账号档位、Stable 或 Preview、价格、配额与开放范围，并更新 `checked_at`。

用户在登录状态下直接看到的产品界面可以记录为有时间边界的直接观察。写清观察时间、入口和账号条件；单个账号可用不能外推为所有地区与账号全量开放。若新观察与旧稿冲突，立即同步修改正文、标题、claim ledger、source-notes 和内容哈希，并使旧批准失效。

## 证据条目

每个会影响结论的事实建立一条内部证据记录：

~~~text
id
neutral_claim
source_url
source_type
publisher_or_speaker
published_at
checked_at
direct_quote_or_support
scope_and_units
uncertainty
independent_chain
~~~

保存原始链接和必要截图。价格、版本、下载量、估值、职位和接口权限会变化，写入检查时间。

## Claim ledger

把正文中的重要句子分成四类：

- fact：来源能直接证明；
- quote：直接引语，以及必须保留发布方、媒体或当事人归属的说法；
- analysis：Frontier Signals 根据材料作出的解释；
- forecast：有事实锚点、以后可以验证的判断。

fact 与 quote 必须有来源。analysis 必须引用支撑材料，并写出适用边界。forecast 要写明观察指标；正文确实需要行动建议时，把成本、风险和适用对象写入相邻的 analysis，不另造无证据的 recommendation。

Claim ledger 的来源与分析字段是内部审计材料，不是公开正文模板。

- `fact` 核实后可以在正文直接陈述；
- `quote` 在正文保留最小必要归属；
- `analysis` 在内部记录支撑材料、推理和边界，公开稿只呈现压缩后的判断与必要事实，不呈现推演过程；
- `forecast` 只写材料支持、边界清楚且以后可以检验的判断。

“这会影响谁、影响什么”同样需要证据。产品入口、价格、岗位流程、采购条件、融资条款、监管义务或可复现行为可以支撑影响路径；仅凭常识推断“所有从业者都会受影响”不算。直接事实按 `fact` 或 `quote` 记录，编辑部连接事实得出的影响按 `analysis` 记录，并写明适用角色、发生条件、时间范围与判断边界。

编辑部亲自完成的测试不伪装成网页来源。把完整条件写进 `article.md` frontmatter 的 `test_runs`，再用 claim 的 `test_run_ids` 关联；外部公告、文档和媒体仍使用 `source_ids`。实测记录不替代对应文章形态要求的公开来源数量。

通过媒体发现的线索，应尽量回到一手材料核实。无法回到一手材料时，保留媒体归属或删除，不能为了让句子自然就把二手报道写成无主语事实。

## 独立证据

两篇文章引用同一个匿名消息，只算一条证据链。两家媒体照抄同一新闻稿，也不能算独立核验。

这些内容至少需要两条独立证据链：

- 融资金额、估值和收入；
- 人事变动、内部冲突与创始人动机；
- 安全事故、违法指控和产品伤害；
- 会影响公司或个人声誉的判断；
- 容易引发交易或采购决定的数字。

达不到要求时，缩小说法或删除。

如果新闻价值正在快速上升，可以把单一可靠独家作为报道对象，写清媒体、信源类型、当事方回应和仍待确认之处。两条证据链的要求约束的是把底层说法升级为事实，不禁止及时报道一条有分量的独家。

## 技术新闻

模型与 Agent 新闻至少检查：

- 产品名、版本、发布时间与可用地区；
- 网页、App、API 和开源权重是否同时可用；
- 上下文、工具、状态、权限、价格和速率限制；
- 基准由谁运行，配置、样本和比较对象是否一致；
- 发布方没有给出的失败率、延迟、成本或人工接管数据；
- 团队是否真的做过独立测试。

开源软件介绍还要检查仓库归属、当前 release 或 commit、许可证、维护状态、系统与硬件要求、依赖锁定、默认网络请求、遥测、密钥和文件权限。需要写“实测”或给操作步骤时，按 [hands-on-reporting.md](hands-on-reporting.md) 完成干净环境安装和代表性任务；README、Star 与他人演示不算编辑部实测。

文章包含编辑部实测、抢先体验或产品对比时，另按 [hands-on-reporting.md](hands-on-reporting.md) 在 `article.md` frontmatter 的 `test_runs` 保存版本、环境、任务、验收条件、重复次数、耗时、成本、失败与人工接管，并用 claim 的 `test_run_ids` 关联结果。没有这份记录，只能写产品观察，不能写成评测结论。

遇到调价时，同时记录现行价格、新价格、生效时间、时段与计费单位。发布方所说的“半价”或“优惠”必须写清比较基线；新方案内部的低档价格，不能直接写成相对现价降价。

把发布方自报跑分写成自报跑分。没有逐题轨迹和独立复现时，不把榜单写成生产可靠性。

发布方未公布的数据，直接写成“公开材料未披露失败率、超时频率或重复成功率”。不要写“这里少了一个数字”“一次和十次差得太远”等作者自问自答。没有实测或公开数据时，不编排“失败、重跑、再次收费”一类假设场景代替证据；机制本身已经由计费规则确认且构成核心分析时，直接写结论，并在 ledger 中标为带条件的 `analysis`。

## 公司与创始人新闻

先画时间线，再解释动机。资料只证明行动时，就写行动、条件和后果。没有当事人自述，不替创始人写心理。

融资报道继续追问：

- 钱是否到账，还是目标规模；
- 股权、债务、算力承诺或二级交易；
- 投资方与公司是否都确认；
- 估值口径是 pre-money、post-money 还是媒体推算；
- 资金准备花在哪里。

## 选题去重

同一事件出现更新时，把它当成同一故事的 revision：

1. 找到当前最新稿；
2. 标记哪些句子已经过时；
3. 记录新增事实；
4. 只保留一个候选发布版本；
5. 旧稿保持 draft 或 superseded，不单独发布。

新标题或新封面不构成新故事。

## 研究完成条件

动笔前至少满足：

- 五件具体材料形成一条可讲清的过程；
- 一条能直接支撑当前新闻状态的来源，可以是一手文件，也可以是有编辑责任且归属清楚的媒体报道；
- 一条独立来源补足限制或背景；
- 观点的反方解释有材料；
- 至少一类目标读者的影响路径有材料支持，并写清发生条件与时间范围；
- 每个易变数字都有时间；
- 每个易变产品状态都在本轮送审前重新检查；
- 无法确认的缺口已经写进边界。

缺一项就继续查或缩短。

## 更正

发现事实错误或状态更新时，停止使用旧版本。记录旧句、新句、原因、时间和来源，同步正文、标题、claim ledger、source-notes 与内容哈希。已发布内容公开写明会改变判断的更正，不悄悄修改。
