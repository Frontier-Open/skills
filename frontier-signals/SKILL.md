# Frontier Signals

把一条前沿新闻或一项值得上手的 AI 工具，做成一篇能让读者迅速看懂全貌、记住一个判断、愿意继续讨论的文章。

Frontier Signals 属于 Frontier World / 前沿之境。默认面向关注 AI 的创业者、产品与技术从业者、投资人、内容创作者和好奇的普通读者。保持编辑部的事实纪律，也保留 Frontier Signals 的编辑判断。

## 默认编辑口径

- 把它写成品牌官号，不写成作者个人号。默认直接陈述判断，不用“我看”“我觉得”，也不为了亲近频繁喊“你”或“我们”。
- 微信公众号文章的 `wechat.author` 默认填空字符串 `""`，不显示作者；只有用户对某篇稿件明确指定署名时才填写。网站的 publisher 仍是 Frontier World，不把出版机构自动写进微信作者栏。
- 自然来自解释顺序、具体材料和句子节奏。完整表达优先，不为短而短，不把主语、条件、比较关系或因果拆成碎句。
- 新闻评论默认解释事件与判断，不自动变成教程、迁移建议或读者工作流。开源软件介绍与实操是独立选题路径；只有选定这一路径并完成真实测试时，才给可复现步骤和结果。
- 不用“先别急着”“真正要争的”“从来不是”等假聊天或翻案句制造张力。判断直接说，依据放在附近。
- 不写“不是……而是……”“不只是……而是……”“看似……其实……”及其变体。也不凭通用行业常识补出“默认执行层”“高频任务主力”“竞争焦点改变”等当前材料没有证明的结论。
- 检索路径、媒体启发、模型卡阅读过程、自问自答和作者内心独白只留在内部材料。公开正文只保留核实后的事实、必要归属与压缩后的编辑判断。
- 用资深媒体工作者的视角写给聪明但未必熟悉该领域的读者。读懂优先于严肃和官腔；标题、第一屏和小标题先写清主体、动作、数字与后果，再决定是否保留术语。
- 拉近距离靠具体场景、白话解释、节奏和事实自身的趣味，不靠频繁喊“你”、故意碎句或作者内心独白。文章应当生动、形象、有趣、实用，同时保持品牌官号而非个人号。
- 校验通过只表示结构与证据合格，不表示文字已经可发。终稿必须只看读者实际看到的正文顺读一遍；凡是像事实台账、查证结论、作者推演或“还缺几类信息”的编辑口吻，移回内部材料或改成读者需要的直接结果。
- 中文写作与终稿冷读先遵守本 Skill 的 [writing-playbook.md](references/writing-playbook.md) 和事实纪律，再强制使用 `$humanizer-zh` 的“媒体与新闻稿专用口径”优化所有公开文字。文字优化不得删除必要归属、时间边界、不确定性或 claim ledger 支撑。
- 30 秒速读、The Signal、固定结尾提问、迁移问题和互动卡都不是栏目模板。文章讲完就停。
- 五件具体材料没有形成可讲清的过程时，不输出标题和正文。先研究；无法研究就缩小题目或明确材料不足，不能用占位符、通用场景和抽象趋势补稿。

## 开工前

1. 确认当前时间与时区。新闻默认使用 Asia/Shanghai。
2. 确认工作目录、目标发布日期、文章负责人和允许执行的外部动作。
3. 检查同一事件是否已有稿件。发现旧稿时先读取其来源与状态，不覆盖未跟踪文件，不把同一轮更新拆成多篇重复新闻。
4. 读取所需参考：
   - 每次都读 [editorial-identity.md](references/editorial-identity.md) 与 [research-desk.md](references/research-desk.md)。
   - 追踪当天新闻、提出选题或审查选题源时读 [source-radar.md](references/source-radar.md) 与 [agent-desk.md](references/agent-desk.md)。
   - 选题或校准竞品时读 [competitor-field-notes.md](references/competitor-field-notes.md)。
   - 动笔前读 [writing-playbook.md](references/writing-playbook.md)。
   - 稿件包含编辑部实测、开源软件实操、抢先体验或产品对比时读 [hands-on-reporting.md](references/hands-on-reporting.md)。
   - 配图与排版时读 [visual-system.md](references/visual-system.md)。
   - 渲染、触碰公众号草稿箱或同步网站前读 [markdown-release.md](references/markdown-release.md) 与 [wechat-release.md](references/wechat-release.md)。

## 固定跨 Skill 复核链

任务只做雷达或研究、不进入成稿时可以停在研究结果；一旦选定题目并继续写稿，按以下顺序执行，不能静默跳过：

1. **选题后先做 dbs 复核。** 选出唯一候选并完成 pitch card 后，把选题、目标读者、发布平台、计划形式、核心材料、差异角度和候选标题交给 `$dbs`。让它根据当前任务只路由一个叶子 Skill 并立即执行完整流程；一般内容选题默认会落到 `$dbs-content` 的五维诊断。只调用 `$dbs` 入口、没有执行叶子 Skill，不算完成复核。形式、标题、表达效率或认知落差出现 `❌` 时，修改角度或放弃选题，不进入写稿。
2. **公开文字齐备后用 humanizer-zh 优化。** 事实、claim ledger、第一版全文、图注和封面文字全部形成后，使用 `$humanizer-zh` 的媒体专用口径处理 `title`、`description`、`wechat.digest`、小标题、正文、图注和封面文字。保留主体、数字、日期、状态、来源归属与不确定性；优化后逐条回查 claim。五维总分低于 45/50 时继续修改，不进入终稿复核。
3. **优化后再做 dbs 终稿复核。** 把 humanizer 处理后的完整公开文字和目标形式再次交给 `$dbs`，由它根据当前具体问题只选择并执行一个叶子 Skill。通用内容复核通常使用 `$dbs-content`；只有已经出现明确的共鸣、口播衔接或发布风险问题时，才分别路由到对应 Skill。解决所有阻断项后才能进入渲染和送审。
4. **改稿就重新闭环。** 终稿 dbs 复核引发任何公开文字修改时，重新执行 `$humanizer-zh` 与 dbs 终稿复核；若修改了事实、角度或新闻状态，先回到材料包与 claim ledger，再重走后续步骤。
5. **留下审校记录。** 在 `source-notes.md` 记录两次 dbs 复核的时间、路由到的叶子 Skill、结论与已处理问题，以及 humanizer 五维评分。公开正文不展示这些内部记录。任一所需 Skill 不可用时，明确报告并保持 draft，不能假装已经复核。

## 一条文章的完整流程

### 1. 捕捉信号

优先检查最近 24 小时，必要时扩展到 72 小时。只追踪这些范围：

- AI 模型、Agent、基础设施、开发工具和能解决具体问题的开源软件；
- 相关公司、创始人、融资、组织与商业动作；
- 会改变产品、工作、资本配置或监管判断的研究与政策。

需要并行研究时，先用 `scripts/init_desk_run.py` 建立有界 `desk-run.json`。最多三个只读 worker 并行，候选最多五个，只选择一个进入写作，每项子任务最多重试一次。Scout、Researcher 和 Reviewer 不得取得微信或网站写权限；定时自动化只能完成雷达与候选包。

每轮选题按 [source-radar.md](references/source-radar.md) 至少扫描五条线：[投资界 AI 频道](https://www.pedaily.cn/i-ai/) 与中文产业媒体、实验室和产品一手发布、研究与开源社区、Bloomberg 等独立商业媒体与监管机构、中英文社交媒体与开发者社区。投资界只负责发现线索；页面还混合自采与转载内容，必须识别原始作者和原始信源，不能把聚合页面自动当成独立证据。署名媒体独家可以直接启动报道，但必须保留媒体归属与未确认状态。社交热度用于估计读者兴趣和发现反方问题，不能替代事实核验。

事件默认仍看最近 24 小时并按需扩到 72 小时。原始材料发布在最近 7 天内，而且过去 24 小时刚在中文或英文社区形成新的高质量讨论时，可以作为 `community-driven` 候选；同时记录原始发布时间与讨论开始时间，不能把旧发布写成当天新闻。只有重复转发、旧链接回流或没有新增讨论的问题，不因热度重新开稿。开源实操候选不强套新闻窗口：它可以由新版本、近期社区需求或一个持续存在的具体痛点触发，但必须核对当前版本、维护状态、许可证和安装路径，不能把多年未维护项目包装成新品。

候选池尽量覆盖产品与模型、公司与资本、研究与开源、政策与现实影响中的至少三类。研究与开源至少区分“发布解读”“项目介绍”和“编辑部实操”，后者必须能回答一个具体读者问题。少于三个合格候选，或一半以上都属于同一类时，把窗口扩到 72 小时并补扫尚未覆盖的信源线；仍没有合格事件就不发，不用边缘 AI 话题凑数。

为候选事件写一张 pitch card：

~~~text
发生了什么
目前最硬的一条事实
这与哪类目标读者有关
会影响他的哪项选择、成本、工作、机会或风险
影响通过什么路径、在什么时间内发生
多数报道漏掉了什么
为什么需要现在知道
标题最能抓住人的事实、冲突或后果
读者会因为什么转给朋友或同事
~~~

按照读者相关性、事件后果、证据质量、时效、社区传播势能、标题传播力、Frontier Signals 独有角度各打 1–5 分。读者相关性是独立硬门槛：至少说清一类目标读者、一个具体影响和一条有材料支持的影响路径；低于 3 分就缩小角度或放弃，不能用“AI 会影响所有人”“行业很重要”补足。社区传播势能与标题传播力不能抬高证据分，但会改变选题优先级。证据质量达到 3 分不要求已有官方公告：有编辑责任的媒体独家、署名调查、当事人发言或可复查的社区材料都可以开稿，前提是把“已经确认”“媒体报道”“匿名消息”和“社区观察”分开。当天没有合格事件时，宁可不发。

选出唯一候选后立即执行“固定跨 Skill 复核链”的选题复核。没有实际执行 dbs 路由出的叶子 Skill，或复核仍有 `❌`，不得进入材料包和正文写作。

### 2. 建立材料包

先研究，再定结论。至少收集五件能推动文章的具体材料。每件记录：

~~~text
claim / source / source_type / published_at / checked_at
direct_support / uncertainty / related_claim_ids
~~~

这是一道开稿门槛。五件材料必须属于当前事件并能共同推动叙述；“速度、成本、能力、稳定性、未来”这类抽象类别不算。达不到时继续研究或缩小题目，不写样稿。

开源软件介绍至少核对仓库归属、当前 release 或 commit、许可证、安装与运行前提、维护状态和一个具体使用场景。写实操时再完成一次干净环境安装和一组可复现任务；只读 README 或转述演示不能写成“实测”。

编辑部亲自完成的实测不是网页来源。按 [hands-on-reporting.md](references/hands-on-reporting.md) 写入 `article.md` frontmatter 的 `test_runs`，并用 claim 的 `test_run_ids` 关联观察结果；它不替代当前文章形态要求的公开来源数量。

官方公告、产品文档、论文、代码仓库、财报、监管文件和完整访谈通常给出最硬的状态边界，但不是所有新闻的开稿前提。有署名、有编辑责任、能说明消息来源的媒体独家可以直接承担报道对象；正文与标题保留“据报道”“消息称”“正在洽谈”等状态，不把尚未确认的底层事件写成完成态。聚合号和纯热度仍只用于发现线索。

涉及融资、估值、人员变动、安全、法律、市场份额或声誉的说法，若要把底层事件写成事实，至少需要两条独立证据链。只有一家可靠媒体的独家或单一匿名消息时，可以报道“某媒体披露了什么”，降低标题的事实承诺并清楚归属；不能因为尚无官宣就自动放弃一个正在形成的热点。

### 3. 选择文章形态

只选一种：

- bulletin：900–1,500 个中文字符。适合单一发布、媒体独家、模型更新或明确公司动作。至少 3 个来源、2 张正文图。
- report：1,600–2,800 个中文字符。适合需要解释机制、竞争关系和实际影响的新闻，也适合完成真实测试的开源软件介绍与实操。至少 4 个来源、3 张正文图；实操稿还必须包含 `test_runs` 和可核验产物。
- profile：2,400–4,200 个中文字符。适合创始人、公司转向或长周期故事。至少 6 个来源、时间线和 4 张正文图。

封面不计入正文图。资料撑不起对应篇幅就降级，不用重复解释补字数。

### 4. 形成观点

先写一句可以被未来事实推翻的判断，再写正文。观点必须同时具备：

- 一组已经核实的事实；
- 这些事实之间的机制；
- 对具体角色的影响；
- 当前不知道的部分；
- 会让判断改变的观察指标。

把反方最强的解释写准确。Frontier Signals 可以有立场，不能把立场伪装成事实。

### 5. 写出第一屏与完整正文

第一屏让读者在 30 秒内得到：

1. 发生了什么；
2. 这会影响哪类目标读者的什么，以及为什么今天值得知道；
3. Frontier Signals 的判断。

后续正文覆盖这些信息：

1. 事件与时间线；
2. 产品、技术或商业机制；
3. 公司、创始人和竞争关系；
4. 受影响的具体角色、影响路径与现实限制；
5. 反方解释、未知和下一步指标。

以上是信息覆盖清单，不是固定段数、小标题或公开结构。让材料决定文章怎样分段。

使用 [article.example.md](assets/article.example.md) 建立唯一公开稿源 `article.md`。YAML frontmatter 保存标题、核心判断、渠道元数据、来源、claims、test runs 和媒体权利；Markdown 正文保存唯一公开表达和图片顺序。微信 HTML、网站 HTML、RSS 与 sitemap 全部从同一文件确定性渲染，不分别改写正文。旧 `signal.json` 只用于历史兼容，不再创建新稿。

研究过程和公开表达必须分层。检索路径、阅读顺序、某家媒体如何启发选题、作者的自问自答与犹豫，以及从事实到结论的逐步推演，只写进 `source-notes.md` 或编辑记录，不进入 `article.md` 正文。公开稿只保留核实后的信息、压缩后的判断，以及读者理解判断所必需的证据。

正文是否写来源名称，取决于说法的证据状态，不取决于作者从哪里看到它。已经核实、无争议且可以独立陈述的事实直接写。直接引语、发布方自报跑分或承诺、单一媒体独家、匿名消息、争议或指控，以及无法独立确认的说法，必须保留最小必要归属。媒体只用于发现或交叉核对时，不写“某媒体也这么说”；模型卡或文档只承担证据作用时，不用“模型卡写得很明白”之类句子展示研究过程。

标题同时承担点击和搜索入口。允许使用强数字、反差、悬念、竞争关系和克制的情绪词，只要读者点开后能在第一屏看到对应事实或清楚的媒体归属。未确认事件在标题中保留“曝”“据报道”“消息称”“或将”“正在谈”等状态；问号不能把传闻洗成事实。主体名称与读者会搜索的核心词尽量放在前半句。

30 秒速读不是每篇文章的固定模块。短 bulletin 和正文已经足够紧凑的 report 默认省略；只有较长 report 或 profile 确实需要一张阅读地图时，才在 Markdown 正文中写一个简短小节，而且不能重复开头。

核心判断写入 frontmatter 的 `thesis` 与正文相应位置，不自动渲染独立判断卡。新闻与第一节已经自然交代判断时，不再重复制作卡片。

局部重点统一用 Markdown `**重点**` 加粗。每段最多一处、全文最多六处，不使用彩色字体，不把整句整段都刷黑。能让读者记住或产生共鸣的句子自然写进正文，仍由附近事实和 claim ledger 支撑；不另做金句卡或“金句”等特殊标签提醒。

第一版完整正文形成后进入配图，并同步写出必要图注与封面文字。全部公开文字齐备后，再执行“固定跨 Skill 复核链”的 humanizer 优化与 dbs 终稿复核。

### 6. 设计图片

每张图只承担一种主要任务：证明事实、展示产品、交代人物或建立必要的概念入口。优先顺序：

1. 官方网页、公告、文档、产品界面的截图，以及官方原始图表和论文图；
2. 权利明确的人物或现场图片；
3. 只有官方素材无法承担必要的非证据型概念表达时，才用 `imagegen` 生成最多一张无文字原创图。

保存本地副本并记录来源、权利、裁切、alt、说明和用途。事实卡不作为 Frontier Signals 的正文图片。AI 图不能充当事实证据，也不能复刻网页、表格、跑分、价格、接口字段或其他需要精确呈现的内容；不要为凑图片数量调用 `imagegen`。

图注默认隐藏。只有证据图、对照组或实测产物离开上下文会难以理解时，才公开一句简短图注，交代图中对象、测试条件或应注意的结果；不显示图源、版权署名或研究笔记，也不重复正文。

图片“高清”同时看源文件和最终阅读效果，不能只看像素数字：

- 优先下载官方可取得的最高分辨率原图。满宽横图有更大原图时，源文件宽度至少保留到 1354 px（677 px 内容列的 2 倍），不得先缩小或用低质量 JPEG 重压；界面与文字截图优先保存为无损 PNG，原始素材本身是 JPEG 时避免反复转码。
- 在 375 px HTTP 预览中以 100% 缩放检查。读者不放大也必须能看清支撑正文判断的界面文字、数字、坐标、单位和关键控件；文件尺寸很大但证据主体只占画面一小部分，仍判定为不合格。
- 横图里的手机、表格或关键局部过小时，从最高分辨率原图紧裁，必要时把同一官方图中的连续状态纵向排列；不得靠锐化、AI 重绘或无信息的像素放大伪装成高清。原图尺寸、最终尺寸和精确裁切范围写入 `source-notes.md`。

官方截图在 375 px 下仍不可读时，按顺序处理：

1. 用移动端视口重新截图；
2. 紧裁到必要原文，同时保留来源、标题、日期、单位和判断所需上下文；
3. 换用另一张可读的官方页面或官方原图；
4. 仍不合适就不放这张图，不制作事实卡，也不用 AI 图冒充证据。

媒体字段 `generated` 只表示是否由生成式 AI 产生。网页截图、官方图片和确定性排版封面均填 `false`。

图片、图注和封面文字确定后，立即执行 humanizer 优化与 dbs 终稿复核。两个门槛都通过以前，不进入渲染；后续新增或修改任何公开文字，都重新完成这两个门槛。

### 7. 校验并渲染

在 Signals 站点仓库运行：

~~~bash
cd /Users/chenjie/Workspace/claire/signals
npm run article:prepare -- /absolute/path/to/article.md
~~~

只对已经完成选题 dbs 复核、humanizer 优化和终稿 dbs 复核的稿件运行该命令。该命令同时校验 Markdown 方言、图片路径、图片权利元数据和渠道字段，并生成微信 HTML 与网站板式预览。校验失败时修改 `article.md`，不绕过规则；修改公开文字后重新完成 humanizer 与终稿 dbs 闭环。

需要人工粘贴到微信公众号时，使用独立的 `frontier-composer` 仓库做最后排版与富文本复制。它直接导入包含 `article.md` 和图片的完整文章目录，不再维护 `wechat.md`。排版工具只负责预览和写入本机剪贴板，不覆盖确定性生成的 `.frontier-build/wechat.html`，也不等于已经保存草稿或发布。

渲染成稿时，判断边界、完整来源与事实台账留在 `article.md` frontmatter 和 `source-notes.md` 供编辑校验，不单独显示提示框。图片只在 media 条目 `show_caption: true` 且 Markdown 图片有必要说明时显示简短图注，始终不显示“图源”或版权署名。正文只有在来源本身能继续帮助读者理解、方法或版权边界需要读者直接查看时，才保留一至三条延伸阅读链接。事实纪律放在后台完成，公开稿优先保持阅读节奏。report 的主标题覆盖全文主要信息面，封面直接出现报道主体名称。

`discussion_question` 是可选的内部编辑提示，不是公开成稿的固定模块。渲染器不自动生成“留给你一个问题”或互动卡。正文确实需要一个问题时，把它自然写进最后一段；文章已经结束时直接收住。

在 `article.md` frontmatter 的 `wechat.topics` 记录一至三个准备添加的微信原生话题，优先选择一个稳定大类、一个报道主体或具体事件，例如 `AI安全`、`Anthropic`。话题名称不带 `#`，不在正文末尾伪装成普通标签。当前官方 `draft/add` API 没有话题字段；使用 API 创建草稿时必须明确提示这些话题尚未添加，并在公众号编辑器中人工添加后复核。

### 8. 复核易变状态

送审、保存远端草稿和正式发布前，重新核对所有会快速变化的事实：网页、App、聊天端、API、地区、账号档位、Stable 或 Preview、价格、配额与开放范围。更新每条相关证据的 `checked_at`。

用户在登录状态下直接看到的产品界面可以作为有时间边界的直接观察，但单个账号可用不等于所有地区和账号已经全量开放。它与旧稿冲突时，以新状态修订正文、标题、claim ledger、source-notes 和内容哈希，记录更正时间；不要保留互相矛盾的旧句。`article.md` 或任一关键图片变化后，微信与网站批准自动失效。

### 9. 预览

使用 HTTP 预览，不直接把 file:// 当成发布效果。至少检查 375 px 和 677 px：

- 标题、导语和小标题没有孤字；
- 正文字号和行距适合手机；
- 图片清晰，无横向溢出；支撑判断的界面文字、数字、坐标、单位与关键控件在 100% 缩放下可读，不要求读者点开或双指放大；需要公开的短图注可读，未启用的图注、图源和脚注没有残留；
- 来源可读，链接没有串位；
- 封面在微信裁切后仍保留主体；
- HTML 与 Markdown 的事实、判断和图片顺序一致。
- 使用本地排版工具时，文章目录中的相对图片全部解析成功，复制后在公众号编辑器中粘贴检查，并在保存草稿、重新打开后确认图片已由微信转存。

### 10. 交付与发布

默认交付本地双渠道稿件包：

~~~text
article.md
source-notes.md
wechat-cover.png
og.png
images/
release.json
.frontier-build/wechat.html
.frontier-build/web/index.html
~~~

`article.md` 是唯一公开内容源；`.frontier-build` 是可删除、可重建的派生物。`release.json` 只保存渠道状态、哈希和远端 ID。

公众号“贴图”是独立的图片消息类型，不是文章正文配图。贴图使用 `article_type: newspic`，由 `scripts/push_image_draft.py` 处理；支持 1–20 张有序图片，首图同时作为封面。每张图先上传为永久素材，再按顺序写入 `image_info.image_list`。贴图的 `draft-package.json`、有序图片字节和完整目标账号同样绑定精确哈希。默认 dry-run；展示标题、纯文本配文、图片数量与尺寸、内容哈希和整包哈希并取得明确确认后，才带 `--confirm` 写入，随后必须通过 `draft/get` 回读。已存在验证草稿时，改变配文或图片只允许核对旧远端快照后 `draft/update` 同一 ID，禁止新建重复贴图。该适配器不发布、不群发、不发送预览。

保存到远端草稿箱属于外部写入，只能在目标公众号、已批准版本和授权会话都明确后执行。使用 Markdown 草稿适配器时，必须先完整读取 [markdown-release.md](references/markdown-release.md) 与 [wechat-release.md](references/wechat-release.md)，并遵守以下顺序：

1. 先运行 `python3 scripts/push_markdown_draft.py /path/to/article`。不带 `--confirm` 时只能 dry-run，不得访问微信或上传素材；
2. 展示 dry-run 给出的目标公众号、标题、精确内容哈希、整包哈希、图片数量、封面和 warning；
3. 针对这一篇稿件、这一目标账号和这两个哈希取得明确确认。开发适配器、配置凭据或以前上传过其他稿件都不构成本次授权；
4. 只在确认后使用 `--confirm --approved-hash ... --approved-package-hash ... --target-account ... --target-principal ... --target-app-id-fingerprint ...` 创建草稿；三个目标身份值必须原样来自同一次 dry-run，凭据只通过进程环境提供；
5. 创建后必须通过官方 `draft/get` 回读。回读通过才记录 `remote_draft` 和 `wechat-draft-receipt.json`；
6. `draft/add` 超时或结果不确定时先协调草稿列表和已有记录，禁止盲目重试；
7. 该适配器止于草稿箱，不发布、不群发，也不发送手机预览。

已存在草稿后，正文、封面或正文图片发生变化时，不得再调用 `draft/add`。先对新整包重新 dry-run 并取得新哈希授权，再使用 `scripts/update_markdown_draft.py` 绑定原 receipt 中的 draft ID 调用官方 `draft/update`；更新前后都通过 `draft/get` 回读，禁止创建第二份草稿。

远端结果不确定时使用 `scripts/reconcile_markdown_draft.py`，它只允许 `stable_token + draft/get`，不得上传素材或更新草稿。若用户已经手动发表，立即停止草稿协调；draft ID 可能已失效，后续只用公开文章 URL 记录发布状态。

若用户已明确说明微信文章已经手动发表、但草稿未完成自动回读，且当前拿不到公开微信 URL，网站仍可通过 Signals 仓库的 `article:publish-manual` 受控上线：先 dry-run 绑定当前 source、WeChat package、site package hash 以及账号名称、主体和 AppID 指纹，再以 `published_unrecorded` 记录人工发表事实并部署网站，不伪造 `sameAs`。拿到公开 URL 后再用 `article:record-wechat` 补录并更新网站元数据。

草稿写入并回读后，由用户在微信公众号草稿箱检查实际结果。用户明确确认当前 draft ID 对应的标题、正文、图片、封面和链接无误后，运行 `npm run article:review -- /path/to/article.md --confirm`；该动作把确认绑定到当前 Markdown、微信 package、网站 package 和 draft ID，然后自动部署 `signals.frontierworld.ai` 并回读文章、首页、RSS 和 sitemap。任一哈希不一致都必须停止。

微信公众号公开发布始终由用户在草稿箱手动完成。代码不得调用 publish、freepublish、mass send 或 preview 接口。网站成功不等于微信已公开；微信草稿授权也不等于微信公开授权。

## 稿件通过线

以下任意一项不满足，保持 draft：

- 第一屏没有事件、读者价值和明确判断；
- 没有明确一类目标读者，或没有明确会改变他的哪项选择、成本、工作、机会或风险；
- 只用“AI 会影响所有人”“行业正在变化”或社交热度制造相关性，没有具体影响路径与材料支持；
- 标题的点击承诺没有在第一屏兑现，或把“媒体报道”“匿名消息”“正在洽谈”写成已经完成的事实；
- 选题后没有通过 `$dbs` 实际路由出的叶子 Skill 复核，或复核仍有 `❌`；
- 标题、摘要、正文、小标题、图注和封面文字没有经过 `$humanizer-zh` 媒体专用口径优化，或五维评分低于 45/50；
- humanizer 优化后没有再次通过 `$dbs` 路由出的叶子 Skill 终稿复核，或仍有未解决阻断项；
- `source-notes.md` 没有记录两次 dbs 复核与 humanizer 评分；
- 重要事实未进入 claim ledger；
- 高风险说法只有一条证据链；
- 观点没有边界或反方解释；
- 材料不足却用通用行业常识、占位符或可套用到任何模型的趋势判断补出正文；
- 图片无来源、权利或用途说明；
- 核心证据图只有名义上的大尺寸，但在 375 px 预览中关键文字、数字、单位或控件仍模糊不可读；
- 文章只换一种说法重复新闻；
- 公开正文暴露检索路径、阅读顺序、媒体对作者的启发、自问自答或推演草稿；
- 应当归属的自报、独家或争议说法被改写成无主语事实；
- 品牌官号被写成个人号，或为了口语感频繁使用第一、第二人称和故意碎句；
- 标题或正文需要读者先懂非常用词、英文缩写、研究术语或行业黑话，且附近没有一句日常中文解释；
- 正文读起来像新闻稿、政策文件、研究摘要、事实台账或编辑会议记录，而不是资深媒体人向普通读者解释一件事；
- 文章只有准确与完整，没有具体场景、读者关系或事实本身的动作与反差，导致内容晦涩、平、远；
- 把普通新闻评论写成教程、迁移清单或读者工作流；
- 把 README、他人演示或一次无法复现的运行写成开源软件实测；
- 出现未解决的时间、价格、版本或身份冲突；
- 送审前没有重新核对易变的入口、地区、账号档位、版本状态、价格或开放范围；
- 公众号预览未通过；
- 外部动作缺少对应授权。

## 语气

像一位见过很多发布会、也愿意把话说人话的资深媒体编辑：清醒、好奇、具体，有一点锋芒。复杂概念先用日常语言讲明白；新闻价值落在人物、动作、数字、选择和后果上。允许幽默，幽默必须来自事实本身。不要模仿任何竞品的句子、标题或视觉模板。Frontier Signals 的目标不是显得最激动或最严肃，而是让读者轻松读懂，并更快拥有一个可靠判断。
